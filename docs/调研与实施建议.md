# SPD 运营异常 Agent：调研与实施建议

日期：2026-09-27。状态：拟采用方案，未完成应用开发、模型实测或服务器压测。

更新说明：本文是早期探索记录，最新范围、工作顺序和模型主选以 [产品与架构底稿](blueprint/README.md) 为准。用户明确要求先完成设计和角色交接，UI 风格确认不等于授权直接开发。

## 1. 产品边界

第一版面向驻点人员和项目经理，处理“数据导入—质量核查—缺货/临期分析—查看证据—确认内部待办—跟踪处理”。从一个真实医院项目的小范围试用起步，合成数据另设演示环境。

当前公开业务证据：公司招聘职责包含库存异常、资质效期、采购流程与运营报表；公开采购公告显示公司参与耗材和试剂配送。公开资料只能确定场景相关性，不能证明内部已有系统缺陷或实际需求强度。[公司岗位](https://gzzyy.bysjy.com.cn/detail/job?career_id=717702&id=3239349)；[2026-09-21 配送结果公告](https://gdhualun.com.cn/gonggao/article?id=10049744-8c0f-44e5-b8c1-cca121ba3d1c)。

医用耗材管理研究参考包括验收效期、定期盘点、按剩余效期发放和追溯。这些原则支持批次、库存状态、记录来源的设计；不把模拟临期天数或采购阈值写成官方规定。体外诊断试剂等产品须按实际分类、说明书和院内制度另行确认适用要求。[卫生健康部门刊载的办法](https://wjw.wuxi.gov.cn/doc/2023/02/13/3881792.shtml)。

## 2. RAG 的位置

引入轻量 RAG，用于检索制度、操作规范、合同交期条款和经批准的产品资料；库存数量、批次、在途和消耗来自结构化数据库，风险由确定性代码计算。

一次分析：鉴权并确定项目范围 → 验证数据时效与完整性 → 查询库存/订单 → 程序计算 → 检索适用资料 → 生成带出处的解释和待办草稿 → 人工确认 → 幂等写入内部待办。

建议检索设计：

- 文档入库：解析章节/表格，保留标题、页码或章节、来源、版本、生效/失效时间、适用项目、审批状态、文档哈希。
- 文本检索与向量检索融合；中文关键词检索必须有中文分词或适配策略，不能直接假定英文全文检索配置有效。
- PostgreSQL + pgvector；小语料优先精确向量搜索，测量规模和延迟后决定是否增加近似索引。
- 检索前过滤项目权限、有效版本和审批状态，再排序；模型看不到无权限资料。
- 检索不到、版本冲突或来源不支持结论时，标出缺口，允许生成“待核实”任务，不自动补编规则。
- 文档内容仅作为证据，不能改变工具权限、执行系统指令或访问范围。模拟提示注入样本单独放入评测集。
- 结构化业务规则版本单独保存。模型从文档提取的新规则先成为待审配置，不能直接覆盖计算规则。
- 合成文档不等于真实公司制度，也不等于注册说明书。真实试点环境不默认启用合成资料。

RAG 首轮评测：适用文档召回、引用支撑度、旧版过滤、无答案处理、跨项目隔离、文档指令攻击。以上仅是评测设计，目前未运行真实模型/向量检索。[pgvector 官方仓库](https://github.com/pgvector/pgvector)。

## 3. Agent 框架建议

拟采用 Python LangGraph 编排单个运营 Agent。它支持确定性步骤与模型步骤组合、状态持久化和人工中断/恢复，适合本项目的待确认流程。框架不负责替代后端鉴权。[LangGraph 概览](https://docs.langchain.com/oss/python/langgraph/overview)；[中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)。

节点建议：authorize_scope → load_and_validate → compute_risk → retrieve_evidence → draft_explanation → validate_evidence → await_confirmation → create_task → finish。

要点：

- 检查点存 PostgreSQL；内部任务及审批记录也是持久化业务数据。
- 恢复时重新核对审批人权限、草稿版本及库存快照；旧快照变化较大时重新分析并确认。
- 任务写入使用业务幂等键及数据库唯一约束；重试或恢复不重复创建。
- 用户和文档都不能指定任意 SQL；模型调用受控查询工具，项目范围由服务器会话确定。
- 有限工具步数、模型超时、取消和成本记录。模型失败时保留规则分析与人工处理能力，并明确标记模型未成功。
- 首版一个 Agent，多种工具；不因不同风险类型就增加多个自治 Agent。

模型与框架分开选择。首轮以允许在目标环境使用、支持工具调用及结构化输出的模型做相同案例对比，单列工具成功率、数字一致性、引用质量、耗时和成本。不要把 OpenAI-compatible 视为所有参数完全等价。

腾讯云模型服务可作为候选；所查混元兼容接口文档包含工具调用/Embedding 示例，并提示新模型能力迁往 TokenHub。落地时以用户账号可用的具体模型、地域和接口能力为准，本轮不绑定旧模型名。[腾讯云接口文档](https://cloud.tencent.com/document/product/1729/111007)。

## 4. 2 核 / 2GB / 50GB 部署方案

后端需要常驻部署，才能提供多用户访问、共享数据库、后台分析和审计。用户现有腾讯云机器可作为精简验证环境，是否足够内部试点必须实际测量。

拟用 Docker Compose：静态 React 前端由 Nginx 提供；单个 FastAPI 进程提供 API、Agent 调用和有限并发任务执行；PostgreSQL + pgvector 同机。首版任务排队状态存数据库，独立模型调用和导入并发限制。

大型模型、向量模型和重型 OCR 不在这台 2GB 机器本地运行。模型/向量通过获准的 API 调用；资料发往 API 的范围和部署区域在接入真实数据前确认。文档先限制文本型 PDF/Markdown/纯文本，扫描件 OCR 另设导入通道。构建前端和镜像尽量在本地/CI，避免服务器峰值编译占用。

初始参数建议：一个 API worker；同时运行 1 个 Agent 分析任务；文档导入串行；小语料精确向量搜索；连接池限制；日志轮转；上传大小与解压后大小限制。这些是待测初值，不是性能承诺。

压测前采集空闲内存、CPU、磁盘、现有容器和负载。若持续内存紧张、出现 OOM 或可接受延迟无法达标，则升级内存或拆分数据库。50GB 同时容纳系统、镜像、日志、资料与数据库，备份应另存，不能把同盘副本当恢复保障。

公开入口只提供 HTTPS 服务；数据库不暴露公网。试点有账号、按医院/角色授权、备份恢复演练与基本日志。部署前还需核实操作系统、地域、已运行服务、域名及访问方式；真实数据试点由公司确认接入范围。[腾讯云 Docker 镜像说明](https://cloud.tencent.com/document/product/1207/79254)。

## 5. 合成数据与验收

合成数据用于开发和反例评测，不能证明真实业务准确率或收益。包含正常库存、缺货、有及时在途、临期积压、过期冻结、零消耗、历史缺失、旧快照、交期未知、部分到货和包装换算。

合成业务数据与恶意/损坏导入样本分开。医院和供应商均使用 SIM 标识，不生成真实注册证、患者信息或冒充正式采购记录。批次总量、冻结/预留、产品基准单位和快照总量要能复算。

试点前验证顺序：

1. 数据夹具完整性与独立预期案例核对。
2. 后端权限、单位转换、批次规则、任务重复提交与恢复测试。
3. 真实模型和检索评测，规则 fallback 单列。
4. 浏览器交互、中文长文本、键盘操作、空状态/失败状态验证。
5. 腾讯云资源与并发实测、备份恢复。
6. 业务人员用脱敏历史案例盲测，再影子运行；核准后才让人员依建议建立真实业务待办。

合成数据阶段只称“试点准备”，接入与核准后才称“真实内部试点”。
