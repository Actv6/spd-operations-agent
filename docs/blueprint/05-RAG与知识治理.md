# 05 · RAG 与知识治理

> 2026-09-27 M1 更新：用户已授权开发，以 [M1 开发交接](13-M1开发交接.md) 为当前范围。先完成本轮最小契约与本地流程，DeepSeek key 后补真实模型验证；RAG 先实际词法检索，向量接入单独验收。下文完整目标不要求在 M1 全部实现。

状态：设计规格；现有知识库只有本地 Markdown 查看和关键词筛选，尚无 Embedding 或向量检索。

技术主选：自建知识治理模块 + PostgreSQL/pgvector + 百炼 text-embedding-v4（1024 维），首版不启用 reranker，详见 [技术选型](11-技术与模型选型.md)。

## 1. 检索什么，什么不放进 RAG

RAG 回答制度、流程、项目条款和获准产品资料中的问题。库存余额、日均消耗、批次效期和在途数从结构化工具查询，不能用过期文档中的数字代替数据库事实。

首版接收 Markdown、TXT、可提取文本的 PDF；合同/产品资料须先有项目授权与可用范围。扫描件、复杂表格解析、图像理解暂列 P1。抽取质量不足的表格不作为数字依据。

演示库全部标记 synthetic_demo，真实试点库默认拒绝混入。公开研究资料、真实内部制度、模拟制度分别标记来源类型，不能靠标题看起来正式就当有效制度。

## 2. 文档生命周期

uploaded → parsed → reviewed → indexed → published；任一环节可进入 failed。已发布版可 retired，修改始终创建新 version。

上传先记录 SHA-256、来源、上传人、项目、文件类型与大小；解析结果展示给维护者，保留章节/页码和段落映射。设置 document_key、version、适用范围和有效起止时间；检查同范围同主题的重叠版本。Embedding 成功且有发布权限才切换发布指针。

“审核通过”和“索引构建成功”必须同时满足才可检索。失败的新版不取代旧版；旧版因业务原因撤销则立即对新检索不可用，不能为了搜索可用率偷偷恢复已撤销内容。

## 3. 片段结构

每个 chunk 必有：chunk_id、document_version_id、org/project scope、source_type、approval_status、valid_from/valid_until、section_path、page（若有）、character_offsets、content_hash、embedding_model、embedding_dimension、index_version。

按标题/章节切分，初始目标 400–800 中文字符，重叠约 80–120 字符；这是实验起点，按文档结构调整。不可横跨不同版本或不同项目的片段。表格保留表头、单位和上下文；不能将表格半行切成缺单位证据。

模型/维度改变时构建独立索引版本，不能把不同向量空间混在同列。完成离线回归后原子切换 active index；保留旧索引以便回滚并受清理策略管理。

## 4. 检索路线

1. 服务器确定 org、project、权限及查询时间语义，先选出可见且适用的 published 文档版本集合。
2. 对问题提取物资编码、业务名词和任务类型；必要时用模型改写，但不得扩大权限范围。
3. 词法路线用中文分词后的词项和编码精确匹配。首版 PostgreSQL `simple` 配置只接收已分词文本，不声称原生英文全文搜索可以直接解决中文。
4. 向量路线在相同授权集合内做精确相似度排序。每路初始 top 20，按 RRF 融合，去重后最多 6 个片段进入回答。
5. 初版先不启用额外 reranker；只有评测表明收益且预算允许时再加。相似分数不是事实置信度，不设无实测依据的万能相似度阈值。
6. 返回原文片段、位置、版本和 evidence_id；保存本次实际检索结果用于复盘，不能事后用更新文档替换历史证据。

pgvector 默认支持精确检索；近似索引以召回换速度，且与过滤组合可能影响返回数量。小语料先选择精确路径，后续启用 HNSW 等要单独测项目过滤后的召回率。[pgvector 官方说明](https://github.com/pgvector/pgvector)

权限过滤必须落实于数据库候选集合和返回结果，不是检索完全部资料再让模型“不要看”。缓存键包含项目、权限版本、知识发布版本与查询语义；撤销权限/资料后使相应缓存失效。

## 5. 回答与引用约束

引用为服务器签发的 evidence_id，并映射到文档版本、位置和文本哈希。前端打开引用通过鉴权接口取对应内容。不要生成无法定位的“根据相关规定”。

输出按 claim 绑定来源。事实只能引用业务工具，制度要求引用知识片段；“建议核实是否有未同步订单”属于行动建议，需与“数据库没查到订单”这个观察区分。

缺材料：返回“未找到本项目有效依据”，显示检索范围及需补充的资料类型；可以建立“请质量人员确认”的草稿，不能把通用常识冒充公司 SOP。

有冲突：保留双方版本/段落，标记 conflicting，停用依赖争议条款的处置建议。业务规则仍按已发布 ruleset 运算，不能由模型选择自己偏爱的制度覆盖规则。

## 6. 时间和规则的一致性

操作建议默认使用当前有效且适用的制度。回溯旧日期时可查询当时版本，并明确标注历史查询；历史版本不得授权现在的行动。

文档 v2 不自动改变结构化风险阈值。维护者提出规则修订 → 人工确认 → 规则测试/业务复核 → 发布 ruleset v2，记录关联文档版本。检索资料与 ruleset 冲突时显示冲突，不隐藏差异。

已发布文档被停用时：新检索立即过滤；未批准草稿失效；已批准但尚未提交的执行在提交前再检并冲突退出；已经建好的任务保留审计历史，提示依据已更新，由负责人复核，不偷偷删除任务。

## 7. 成本、攻击与质量

文件哈希和 chunk 哈希用于重复导入/Embedding 去重；分批串行构建，在 2GB 机器上不常驻向量模型。记录每次向量请求量、tokens/字数计费依据和失败重试。

防护用例包括：文档里要求忽略系统规则、片段要求访问外部地址、资料伪造授权、过期版本高度相似、跨项目编码一致。模型不能将文档指令转为工具权限，也不能自动抓取文档里的链接。

验收分别测召回、排序、引用定位、引用支持度、无答案、冲突和跨项目泄漏。人工标注与可复算检查是主依据，LLM judge 只能辅助；见 [评测规范](07-评测与验收.md)。
