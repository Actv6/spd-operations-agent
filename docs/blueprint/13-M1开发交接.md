## 3. 架构和可维护性

- React/TypeScript 前端；FastAPI/Pydantic 后端；SQLAlchemy/Alembic；PostgreSQL 作为目标数据库；LangGraph 只管理 Agent 流程。
- 后端按 auth、projects/data、agent、knowledge、providers 分模块；API 与同仓库轻量 worker 分进程，数据库持久队列。队列领取、重试与任务结果防重复要有最小验证，不引入 Redis 或微服务。
- 前端只认识项目 API。供应商参数只在 provider adapter 内；库存计算、鉴权、引用校验是确定性代码。
- 开发前先落地本轮最小 OpenAPI/请求响应/错误契约，与前端类型和工具 Schema 同步。使用 06/12 的稳定 run/event/result 形状；未实现的业务 API 不冒充可用。
- 为本轮实现锁定真实依赖版本，提供迁移、种子数据、启动和测试说明；不得把未测依赖组合写成已兼容。
- 优先真正运行 PostgreSQL。若环境无法启动 PostgreSQL，可增加明确标注的 SQLite 本地开发配置继续完成垂直流程，但保留 PostgreSQL 迁移及运行配置，单列 PostgreSQL/pgvector 未验证，不得宣称等效通过。不得为绕开环境问题重建一套架构。

## 4. 注册与权限的最小规则

本地演示开放注册，新账号仅创建自己的隔离演示组织/项目，不加入已有公司或其他用户项目，不赋全局管理员。本人演示项目可加载现有合成数据；项目 ID、用户 ID 和角色都由服务端确认。真实公司公共项目的邀请/审核/SSO 留待试点阶段。

密码使用成熟哈希库；会话优先 HttpOnly Cookie，同源开发代理，写请求有 CSRF 防护，登录与注册限流；生产 Secure Cookie 配置与本地 HTTP 开发区分。密钥与密码不写日志或仓库。不扩展邮件/SMS 验证、第三方登录和密码找回服务。现阶段身份流程只代表本地演示条件。

## 5. DeepSeek 和无 key 时的边界

配置建议：`LLM_PROVIDER=deepseek`、`DEEPSEEK_BASE_URL=https://api.deepseek.com`、`DEEPSEEK_MODEL=deepseek-flash`、`DEEPSEEK_API_KEY`。这是当前官方文档的可配置模型标识；得到 key 后以账号 `/models` 和真实调用验证。API key 只在后端本地环境或密钥管理中配置，不进入 Vite public 变量。

先用非思考模式、受控 tool calling、JSON 输出与 Pydantic 校验；不假定普通 Chat 接口支持所有 JSON Schema strict 能力。实现显式 mock provider 用于离线合同与流程测试；真实 provider 缺 key 返回明确配置错误，不能悄悄退回 mock。`mock`、`model`、`rules_only` 必须在运行结果和 UI 中可区分。

没有 key 不阻塞 A–E 的工程验证；但真实模型工具选择、回答质量、token、费用、延迟仍是未验收项。用户提供 key 后仅补真实模型联调与评测，不把缺 key 当成重新征求开工许可的理由。

## 6. RAG 先实现可验证的检索

DeepSeek 生成模型 key 不等于其他厂商的 Embedding key。M1 用实际中文词法检索构建文档→分块→权限/有效版本过滤→检索→引用的链路；真实模型接入后可在此基础上完成检索增强生成。无 key 阶段的生成用 mock 标注，但文档存储与检索本身必须真实执行。

Embedding provider + pgvector 存储/迁移设计保留，后续可用单独配置的 `text-embedding-v4` 1024 维。未配置时不生成随机或哈希向量假装语义检索、不在 2GB 服务器下载大模型；接口返回实际 retrieval_mode。向量与混合检索接入后单独回归，M1 不强制增加第二家付费账号。

最小文档摄入先支持现有 Markdown/纯文本和可复现 CLI，无须先写复杂上传/OCR平台。文档记录 source_hash、版本、synthetic 标签、所属项目、生效区间；引用至少带文档/版本/chunk/章节及可回查原文。查询缺依据或来源冲突时不得编造制度。检索文本是资料，不是可执行指令。
