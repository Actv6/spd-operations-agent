# 10 · 角色协作与交接机制

> 2026-09-27 M1 更新：用户已授权开发，以 [M1 开发交接](13-M1开发交接.md) 为当前范围。先完成本轮最小契约与本地流程，DeepSeek key 后补真实模型验证；RAG 先实际词法检索，向量接入单独验收。下文完整目标不要求在 M1 全部实现。

版本：v0.3-review。以下是责任与交接设计，不代表已经有真实团队或多个开发 Agent 在执行。目前仍处于文档阶段。

## 1. 角色不是称呼，而是产物责任

| 角色 | 主要负责 | 必须交出的产物 | 必须参与的评审 |
|---|---|---|---|
| 产品经理 PM | 场景、范围、优先级、业务术语、验收口径 | PRD、用户故事、需求编号、流程、排除项 | UI、接口是否支持业务、验收结果 |
| 产品/交互设计 UX | 页面结构、用户行动、状态与反馈 | 第三种风格的页面规格、交互状态表 | 运行/失败/审批冲突/窄屏体验 |
| 架构/技术负责人 TL | 技术边界、契约、版本、一致性、成本 | ADR、依赖关系、接口基线、集成方案 | 所有跨模块变更与发布 |
| 后端工程师 BE | 身份、数据、规则、审批、任务、队列 | 数据模型、HTTP API、领域服务、迁移及测试 | 与 FE/AI 的参数和错误语义 |
| Agent/RAG 工程师 AI | 图编排、工具调用、检索、证据回答、模型适配 | 工具 Schema、运行事件、结果 Schema、提示词/检索版本 | 与 BE 的工具及审批边界；与 FE 的展示事件 |
| 前端工程师 FE | 工作台、过程、证据、草稿审批、任务交互 | 按契约调用的界面、状态处理、组件检查 | API 消费、错误/重连/异步结果 |
| 测试/评测工程师 QA | 独立用例、接口、流程、AI 质量、回归 | 测试计划、保留集、缺陷、复测与验收报告 | 从需求评审开始介入，不只在开发结束介入 |
| 发布/运维 OPS | 环境、部署、日志、备份恢复与回滚 | 环境清单、部署记录、监控与恢复证据 | 资源和发布门槛 |
| 业务负责人/用户 | 确认真实业务与是否适合试点 | 范围确认、真实口径、授权资料和试用反馈 | 设计基线、影子运行和试点验收 |

一个人或一个 AI 可以承担多个实现角色，但角色产物仍分开。实现者的自测不自动等于 QA 通过；若由同一助手做复核，报告必须明确“独立复核步骤，非独立人员”。后续若安排子 Agent，按有边界的交付包分工，并保留实际审阅者和证据，不能用虚构签字代替验收。

## 2. 阶段与门槛

| 门槛 | 工作与产物 | 退出条件 | 当前状态 |
|---|---|---|---|
| G0 需求基线 | PM/UX 完成 01/02，QA 写反例 | 场景、角色、主流程、失败分支、范围和验收一致 | 文档已整理，待用户评审 |
| G1 架构/契约基线 | TL/BE/AI/FE 审阅 03–06、11、12 | 技术主选、业务对象、参数、状态、错误和示例无歧义 | 评审稿，未冻结 |
| G2 兼容性验证 | 在允许开始技术验证后，用合成数据跑最小 PoC | 主选模型的工具/Schema/中文引用通过；锁依赖与账号地域 | 未执行，不等于主选未定 |
| G3 分工实现 | FE、BE、AI 在已冻结契约下并行 | 每个纵向闭环可联调，不能各做完后才第一次连接 | 未开始 |
| G4 独立验收 | QA 回归、AI 保留集、失败恢复、资源测试 | 无未解决 P0/P1，关键边界通过，报告可复现 | 未开始 |
| G5 影子与试点 | OPS 部署，业务人员复核 | 授权数据、访问范围、备份恢复与业务验证满足 | 未开始 |

G0/G1 完成并获得明确开工指令后才做 G2；G2 是短小的技术兼容性验证，不借机铺开 UI 和 CRUD。G2 通过后进入 G3。开发过程中不需要每个小函数向用户请示；只对业务范围、技术主选或对外行动的实质变化重新同步。

## 3. 三条开发线如何同步

**BE ↔ AI**：BE 提供 ToolContext、结构化库存/批次/订单查询和风险运算；AI 提供 ToolRequest/ToolResult Schema、调用预算和错误分类。BE 的服务函数可被 HTTP 和 Agent tool adapter 共用；Agent 不绕过服务直接拼 SQL。批准写入由 BE 应用服务执行。

**BE ↔ FE**：共享 HTTP OpenAPI、DTO、错误码、分页、时间/数量格式、乐观锁和幂等规则。FE 从同一契约生成类型和 mock，不凭聊天记录自己猜字段；BE 对固定请求/响应样例做契约检查。

**AI ↔ FE（通过 BE API）**：AI 定义稳定的业务事件与结果对象，BE 验证、存储并投影成 API；FE 消费 run_id、状态、进度、analysis_id 和 draft_id。FE 不直接访问模型密钥、LangGraph 端口或供应商 SSE 格式。

**QA ↔ 三条线**：在实现前拿到正常、缺失、超时、越权、冲突、取消和重复提交样例。测试验证契约与业务结果，而不是接受“我的模块返回 200”作为完成。

## 4. 每次交接的固定内容

交接包必须记录以下字段，缺必需项就退回补充：

```text
交付编号 / 需求 ID / 当前版本与状态
提交角色 / 接收角色 / 实际审阅者
输入资料和采用的契约版本
本次交付内容与文件路径
请求、响应、事件、错误的最小样例
自测证据 / 未验证项 / 已知缺陷
依赖项 / 阻塞项 / 兼容范围
验收条件 / 审阅结论 / 日期
```

交接状态：draft → ready_for_review → accepted 或 changes_requested → implemented → verified。`accepted` 仅说明设计可实施，不能提前填 `verified`。

PM 交接给开发时附 Fxx、页面 Pxx、流程 Jxx 和验收；开发交给 QA 时附契约版本、数据种子、真实执行命令、结果和限制；QA 交给发布时附缺陷清单、回归范围和未验证风险。

## 5. 接口变更流程

任何一方发现需要改字段：提交 CR → 说明业务原因/影响消费者 → 先改规范和例子 → FE/BE/AI/QA 审阅影响 → 更新版本和迁移策略 → 同步 mock/类型/实现/测试 → 联调确认。

字段改名、类型改变、枚举改变、含义改变即使 URL 不变也是契约变更。新增可选字段可以兼容发布；删除字段/改变语义要有版本或迁移窗口。不能一方口头说“我已经改了”就让另一方追着修。

## 6. 协作纪律

- 当前仓库文档是共同依据，聊天只记录决策，决定必须回写文档。
- 不同实现角色优先修改各自模块；跨模块契约由 TL 协调，不同时各改一份 DTO。
- 每个功能先纵向联通，再增加数量；不会等所有后台页面做完才连接 Agent。
- 开发前读验收；开发中看契约差异；开发后提交证据；修复后由 QA 复测。
- 项目里的运营 Agent 数量仍为一个；开发角色多，不代表运行产品必须堆多个自治 Agent。

## 7. 需求到交付的追踪入口

以下是待实施的验收分组，不是已执行测试数量。交付包必须引用这些需求号，避免只按“前端完成/后端完成”统计进度。

| 需求 | 主要页面/流程 | 共同契约 | QA 验收组 |
|---|---|---|---|
| F01 身份/项目 | 全局项目选择 | me/projects、项目授权上下文 | T01 跨项目、撤权、登录状态 |
| F02/F03 导入/质量 | P05 / J01 | imports、snapshot、quality_issue | T02 原子发布、重复导入、缺失与坏数据 |
| F04 风险 | P02/P03 | compute_risks、metrics、finding_version | T03 G01–G09/G11 数值与边界 |
| F05 运行 | P01/P02 / J02/J07 | runs、events、answers、cancel | T04 澄清、超时、取消、恢复 |
| F06 检索 | P02/P06 / J03 | search_knowledge、evidence | T05 G10/G12–G14、引用与权限 |
| F07 回答/追问 | P02 / J03 | analysis、parent_run、coverage | T06 数字一致、遗漏、依据支持 |
| F08 审批 | P04 / J04 | draft_revision、approval、idempotency | T07 重复、并发、过期依据、迟到提交 |
| F09 任务 | P04 / J05 | task 状态、result、revision | T08 完成、重开、异常与任务分离 |
| F10 知识治理 | P06 / J06 | document_version、publish、retire | T09 失败索引、重叠版本、撤销 |
