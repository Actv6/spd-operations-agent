## 1. 按纵向闭环组织开发

| 工作包 | 依赖 | FE / BE / AI 协作 | 交给 QA 的结果 |
|---|---|---|---|
| WP00 设计冻结 | 当前文档 | PM/TL 统一范围；BE/AI/FE 固定接口与样例；QA 固定用例 | 需求、契约、模型主选、验收可一一对应 |
| WP01 G2 最小技术验证 | WP00 + 明确允许开始验证 + 可用 API 配置 | AI 验证主选模型工具/结构化输出/Embedding；BE 验证持久化恢复接口 | 兼容性记录，精确依赖锁定；未通过不铺开功能 |
| WP02 事实与规则闭环 | WP01 | BE 实现最小身份/项目/导入/规则；AI 对接受控读取；FE 按契约完成范围与数据质量查看 | 一组数据可导入、发布、查询和精确复算 |
| WP03 一次只读 Agent 分析 | WP02 工具 + WP01 模型 | AI 编排运行与预算；BE 排队和事件投影；FE 发起/取消/查看结果 | 真实模型调用可追踪，失败有降级，不假扮成功 |
| WP04 RAG 证据闭环 | WP03 主路径 | AI 检索与引用；BE 文档版本/ACL/发布；FE 引用查看和知识预览 | 有出处、有版本、有权限、无答案时能停止 |
| WP05 建立与处理内部任务 | WP03/04 | AI 产草稿；BE 审批事务/幂等/任务状态；FE 审阅、分派和结果反馈 | 未批准无任务；重复/恢复唯一；并发变化要重审 |
| WP06 回归与试点准备 | WP02–05 | QA 独立回归；各线修复；OPS 部署与恢复；业务影子验证 | 可复现报告、资源实测和发布/回滚清单 |

每个包可在契约接受后并行推进三条线，集成时机按小闭环而非角色分段。FE 可以先消费共享 mock；mock 通过只是界面/契约验证，必须再连真实 BE+AI。

不先做完整 ERP/采购后台；主路径需要多少管理能力就先做多少。岗位和角色复杂度通过最小能力集表达，避免把所有时间用在菜单和报表。

## 2. 未来代码边界（仅建议布局）

```text
frontend/src/
  features/agent, evidence, drafts, tasks, data, knowledge
  api/generated             # 从契约生成，不手改
  components                # 共享显示控件，不放业务规则
backend/src/
  api                       # HTTP / 会话 / DTO 映射
  application               # 发起分析、审批、导入发布等 use case
  domain                    # 风险、单位、状态转移、权限策略
  agents                    # graph、状态、节点、tool adapters
  knowledge                 # 解析、分片、检索与引用
  providers                 # 模型/向量/文件等外部适配
  infrastructure            # repositories、jobs、checkpoints
contracts/
  openapi.yaml              # 对外 API 唯一基线
  schemas                   # 工具、事件、结果 JSON Schema
  examples                  # 正常、错误、冲突、降级样例
prompts/                    # 命名版本及变化说明
evals/                      # 开发集、受控保留集、指标与报告
deploy/                     # Compose、环境模板、发布/恢复说明
docs/blueprint/              # 产品、设计和 ADR
```

不为预期中的所有扩展预建空模块。现有 frontend 的模拟数据和硬编码场景以后通过 adapter 替换，不能继续向单一 App 文件堆所有功能；也不必无理由全部推倒重写。

## 3. 契约与版本的唯一来源

设计阶段先在 06/12 评审字段，G1 产出 `contracts/openapi.yaml` 与 JSON Schema/样例。此后 API 契约是前后端共同基线；BE 的 Pydantic/运行时 OpenAPI 必须通过语义一致性检查，不能直接覆盖基线抹掉差异。FE 类型和 mock 从基线生成。

独立记录：code_version、api_contract_version、tool_schema_version、graph_version、prompt_version、ruleset_version、model_release_id、knowledge_release_id、index_version、fixture_version。每个 run 保存当次组合，模型/文档更换后可以定位影响范围。

v1 URL 并不允许任意变字段；破坏性改变按 CR 和迁移窗口处理。知识内容、规则阈值和提示词是三种版本，不能更新一个就默默修改另两个。

## 4. 开发与交接的完成定义

一个需求完成必须具备：实现与需求对应；API/工具/事件符合约定；成功、空、错误与取消可处理；权限和写入约束被测试；自测证据和已知限制完整；没有把真实模型失败隐藏为 mock 成功。

一个迭代完成还需 QA 回归、引用/工具/事务评测和关键缺陷复测。上线完成则另需部署、访问、日志、备份恢复和业务验收。不能用同一个“完成”状态覆盖这些不同阶段。

## 5. 提交、审阅和变更

每个变更包列出：需求/CR 编号、影响模块、契约变化、实现说明、验证命令/证据、未验证项、回滚方式。跨模块共用文件先明确负责人；并行任务不各自维护一份不同的工具签名。

Schema、计算、权限、审批、引用、重试和版本切换要有有意义的测试；单纯低风险文字/样式无需堆重复实现的测试。任何模型/提示词改动先跑开发回归，再受控跑保留集；不能针对同一保留答案无限调参后仍称独立评测。

## 6. 维护与回滚

- 模型发布：先部署新 adapter/配置的测试版本→同集回归→受控切换→观测；失败回旧发布或 rules_only，记录切换原因。
- 索引发布：新索引构建与评估完成后切指针，维度/模型变化不能覆盖旧向量；数据库真相和历史引用不随索引回滚被改写。
- 应用/数据迁移：优先新增兼容字段，再迁移消费者，最后弃用；数据迁移要有备份和恢复策略，不假设所有迁移都可无损 down。
- 队列/checkpoint：定义保留期和清理作业，活跃等待批准的状态不因普通清理消失；业务审计的保留期由公司要求确定。
- 配置：模型密钥、账号、端点在服务器配置中注入；环境模板只放占位。不得将真实密钥或内部样本放进仓库/前端包。
- 观测：run_id/trace_id 串联日志；记录步骤耗时、工具错误、模型成本、fallback、队列积压和磁盘。默认只记录必要字段，外部观测平台另行授权。
