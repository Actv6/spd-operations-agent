# 01 · 产品需求与范围

状态：v0.2-review，目标产品设计；不是当前实现清单。

## 1. 定位与问题假设

产品暂称「SPD 运营异常 Agent」。服务对象首先是医院项目驻点人员、项目经理，以及处理交期和效期问题的商务/质量人员。

待验证的问题是：核查一次异常需要交叉查看库存、批次、消耗、在途和制度；信息不完整时难以知道下一步找谁补什么；建议和后续处理容易脱节。我们尚未获得内部访谈，不能声称这些问题已在该公司被证实。

核心价值不是多一个报表，而是把运营人员的一次核查工作组织成可追溯流程：回答“哪项值得处理、为什么、证据是什么、还缺什么、下一步由谁确认”。

## 2. 首版闭环与边界

首版包含三类风险：缺货核查、未开封库存批次的临期/过期核查、数据质量异常。交期不明及部分到货是核查分支，不扩展为完整采购系统。

首版有三种入口：手工点击“分析当前快照”、对选中异常追问、输入自然语言运营问题。定时巡检留到后续阶段，先证明一次分析可信。

输出限于分析卡片、引用、缺口清单和内部待办草稿；人工批准后创建内部任务。采购下单、调拨、库存调整、报废、临床使用建议及对外消息发送不在首版范围内。

只处理供给运营信息，不引入患者记录。没有开封/上机/温控数据时，不宣称覆盖试剂全生命周期或判定物资适用性。

## 3. 用户与权限设计

身份和医院项目成员关系由服务器确定，页面上的医院下拉框不是授权机制。权限暂按能力定义，岗位到能力的映射待业务确认。

| 角色 | 核心工作 | 默认能力 |
|---|---|---|
| 驻点人员 | 发起核查、补充事实、处理分派任务 | 查看所属项目、分析、提草稿、更新分给自己的任务 |
| 项目负责人 | 审阅建议、分派和确认闭环 | 所属项目全部任务；批准/拒绝草稿；关闭、取消、重新打开任务 |
| 商务/质量协作人 | 补交期、核对效期处置要求 | 查看获准项目资料；处理分派任务；不默认有全部审批权 |
| 知识维护人 | 整理文档版本和适用范围 | 上传、修订、申请生效；发布能力单独授权 |
| 平台管理员 | 账号、配置、运维 | 不因管理员身份自动获得所有项目业务内容 |

任务可由负责人分配给有项目权限的用户。权限在每次读取、导出、恢复运行和写入时重新检查，不能只在登录时判断。

## 4. 功能需求

P0 指进入真实内部试点前必须完成；P1 为闭环稳定后的增强，不是当前已承诺实现。

| ID | 优先级 | 功能与输入 | 用户得到什么 | 验收要点 |
|---|---|---|---|---|
| F01 | P0 | 登录及项目选择 | 仅属于自己的项目空间 | 无项目权限时 API、文档和运行详情均不可读 |
| F02 | P0 | 导入一组库存/批次/消耗/订单文件 | 导入报告、可用的版本化快照 | 先预检再发布；行错误可定位；坏文件不能覆盖现行快照 |
| F03 | P0 | 数据质量检查 | 缺日、旧快照、单位冲突、字段缺失清单 | 缺失不当零；受影响的预测停止，正常对象可继续 |
| F04 | P0 | 结构化异常识别 | 缺货/效期候选与计算证据 | 数字由代码复算；及时在途、冻结、单位和时点影响明确 |
| F05 | P0 | 一次自然语言核查或当前快照分析 | Agent 分步骤运行、必要澄清、可取消 | 区分问题理解、查数据、检索、整理结果；实际运行可追踪 |
| F06 | P0 | 适用制度与资料检索 | 带来源、位置、版本和时间的证据 | 无授权或停用资料不能进入普通回答；缺依据时明确不足 |
| F07 | P0 | 证据化分析与多轮追问 | 结论、指标、解释、建议动作和未知项 | 数字绑定工具结果；追问沿用范围，刷新数据须产生新分析版本 |
| F08 | P0 | 草稿审阅与批准 | 可编辑的内部任务、明确批准结果 | 未批准不落业务任务；重复批准不重复建任务；过期证据须复核 |
| F09 | P0 | 任务处理与结果反馈 | 分派、开始、完成、关闭与重开记录 | 完成必须有结果；完成操作不自动等于异常已消失 |
| F10 | P0 | 知识版本与发布 | 解析预览、权限、生效时间、索引状态 | 文档入库不等于可检索；发布后才进入新查询 |
| F11 | P0 | 运行记录与评测观测 | 模型/规则结果、工具状态、成本和失败类别 | 不把 fallback 计为模型成功；用户看进度摘要而非隐藏推理 |
| F12 | P0 | 反馈、审计与运行开关 | 纠错记录、版本追溯、AI 停用入口 | 反馈不直接训练或改规则；停 AI 后仍能人工核查 |
| F13 | P1 | 定时巡检与站内摘要 | 新异常与变化汇总 | 去重、限频、失败可见；本稿不实现邮件或外部消息自动发送 |
| F14 | P1 | 更深场景与集成 | 脱敏系统对接、OCR、退库/调拨等 | 每增加一种数据或行动都补权限、规则与评测 |

F01/F02/F09/F10 的管理界面尽量克制，仅提供让 Agent 可用、可解释、可维护的必要功能。

## 5. 用户故事与验收示例

**US01：驻点人员问“今天检验科有什么要先处理？”** 系统按当前已发布快照识别候选，Agent 选择需要核查的库存/批次/订单工具，返回按规则优先级排序的摘要。不能因为模型未调用工具就声称完成全项目巡检。结果应声明扫描范围、跳过对象及缺失字段。

**US02：问“生化清洗液为什么有风险？”** 使用模拟 G01：可用 120 瓶，完整 14 天日均 20 瓶，基线覆盖 6 天，交期 8 天，快照内无在途。解释为“有需核查的供应缺口”，引用模拟制度；不自动声称现实中一定断供或已下补货单。

**US03：问“这种试纸临期怎么处理？”** 展示批次、到期日期和模拟估计，再检索项目有效的效期处理资料。没有对应批准制度时只建议补充核查，不能自拟报废授权。

**US04：负责人批准草稿。** 审阅负责人、截止时间、措施、来源和影响范围；批准成功返回任务编号；再点一次返回同一结果。期间数据更新则提示差异并要求审阅新草稿。

**US05：消耗记录缺两天。** 返回数据缺口和补录任务建议，不输出看似精确的库存覆盖预测。补齐并发布新快照后可重新分析，旧记录保留。

## 6. 成功标准与取舍

技术成功：工具参数和数字可验证、检索到适用证据、引用确实支持结论、无依据时能停止、恢复不会重复写入。业务成功：人员能更快完成核查且错误率可接受，须经脱敏历史案例和实际试用测量；当前不填写提升百分比。

试点候选数据规模先按单项目、最多 500 种物资、10,000 个知识片段设计，作为负载测试目标，不是 2GB 机器的容量承诺。实际规模超出则调整检索、分批分析或资源，不能默默截断后声称分析全部。

版本推进：合成数据验证版 → 经批准的脱敏影子运行 → 有限人员的内部待办试点。阶段之间的验收分别记录，不能以界面完成或构建成功跳级。
