## 1. 通用约定

- ID 使用服务器生成的稳定标识；产品展示名不能作为关联键。现有 SIM 字符串可作为 external_code 导入。
- 业务时间存带时区时间戳，展示使用项目时区（试点默认 Asia/Shanghai）；效期是 date，含义由规则明确。
- 数量使用 Decimal/NUMERIC 和单位，不用二进制浮点直接相等判断；包装换算版本化。
- 所有业务事实可追到 source_import_id、source_row、snapshot_set_id；更正生成新版本，不原地覆盖历史分析依据。
- org_id/project_id 服务器侧校验；所有跨表关系检查同一组织/项目，不能只凭外键存在认为合法。
- 数据标签明确 synthetic / approved_real；二者不在同一试点查询中混用。

## 2. 核心对象与关系

| 对象 | 关键字段 | 约束/用途 |
|---|---|---|
| organizations / projects / memberships | org、hospital/project、user、capabilities、permission_version | 项目成员关系与能力；project 对应首版医院项目 |
| products / unit_conversions | code、name、spec、base_unit、purchase_unit、factor、version | factor > 0；未知换算不能猜；同名不同编码分开 |
| import_jobs / import_rows | type、file_hash、source_time、mapping_version、status、errors | 项目+类型+哈希去重；保留预检报告 |
| snapshot_sets / snapshot_versions | project、as_of、source_versions、published_at、quality_status | 一组一致分析输入；current 指针发布时原子切换 |
| inventory_positions | snapshot、department、product、available/frozen/reserved | 唯一粒度为快照+项目+科室+产品；批次汇总可复算 |
| inventory_batches | lot_code、product、department、expiry_date、on_hand/frozen/reserved、status | 不可用批次不能计入可用量；数量均为基准单位 |
| consumption_daily | day、quantity、record_type、department、product、source | 一条完整观察记录可以为 0；缺行是未知；退库单独类型 |
| purchase_orders / order_lines | expected_date、confirmation、ordered/received/cancelled、unit | 未到量=订购−到货−取消，不得为负；同日数据口径对齐 |
| ruleset_versions | version、thresholds、calendar、effective_at、approved_by | 计算规则独立于提示词与文档 |
| findings / finding_versions | type、subject、ruleset、snapshot、severity、status、metrics | 身份与版本分开；同一问题后续分析产生版本，不覆盖历史 |
| documents / document_versions / chunks | key、version、scope、validity、hash、index_version | 版本发布与 ACL；重复/冲突明确处理 |
| agent_runs / run_events / tool_results | mode、parent_run、versions、status、usage、cursor、evidence_refs | 记录模型是否真正运行、事件顺序和覆盖范围 |
| evidence / metrics | source_kind、source_id/version、location、hash、value、unit、formula | 引用必须绑定不可变来源；数字来源可核验 |
| action_drafts / draft_revisions | analysis_id、finding_version、title、steps、owner、due、evidence_hash | 修改产生 revision；批准针对精确版本 |
| approvals | draft_revision、actor、decision、status、idempotency_key、task_id | status 为 pending/committed/conflicted/rejected；可查询结果 |
| tasks / task_events | approval_id、finding_id、owner、status、result、revision | approval_id 唯一；多次提交不创建重复任务 |
| feedback / audit_events | actor、target_version、category、before/after、trace_id | 日志可追溯；反馈不直接改规则 |
| jobs / graph_checkpoints | run_id、lease、attempt、fencing_token；图状态 | 队列恢复和编排存储，不是业务任务状态的替代 |

同一个物资可有不同异常；缺货、效期、数据质量不能用“产品 ID”互相覆盖。重复候选用 project+subject+type+ruleset 的开放异常关联策略，并保留各 snapshot 的 finding_version。不同批次效期问题的 subject 包含 batch_id。

## 3. 首版计算契约

**可用库存**：released 且未过期批次的 `on_hand - frozen - reserved` 之和。三者均非负，冻结与预留不能重复占同一数量；超额或无法解释的状态触发数据错误。冻结/过期批次的可用量为 0。

**消耗**：以快照所在项目日为 D，取 D−14 到 D−1 的完整自然日。14 天齐全才给日均；零日均返回不可估计，不返回无穷覆盖；退库冲正先规范为定义明确的流水，不直接混作负需求。

**覆盖基线**：available / avg_daily，只用于说明，不等于精确断货日期。交期缺失只阻止依赖交期的判断，不阻止展示已有库存或检查效期。

**逐日模拟（待实现）**：首版采用明确的日桶假设。在分析起点之后每个日桶，先剔除当日已不可用批次，再加入已确认且当日可用于发放的在途，再按 FEFO 消耗；记录最早未满足需求及原因。不假设仅有“预计日期”而无确认状态的订单必然到货。

当源数据只有日期没有时刻时，必须把到货在需求前的假设写入结果；同日时点不确定会形成核查项。当天剩余需求无可靠数据时不输出精确今日断货判断，未来完整日桶与起点口径一并展示。已有 G02 仅验证约定日桶示例，不能扩张为现实服务保障。

**效期**：演示 expiry_date 为最后可用日期，expired 判断为 expiry_date < D；是否符合实际产品要求待确认。临期阈值按已发布规则配置；开封后稳定期未建模。G03 的“未来 10 天后剩余 250 筒”不是承诺应报废的数量。

**快照质量**：超时、批次汇总不一致、计量单位未知、历史缺日，分别产生结构化 quality_issue。阈值初值来自模拟规则，不当作法规。

## 4. API 通用协议

前缀 `/api/v1`。读取分页采用 cursor/limit（默认 50、最大 200）；错误形状统一：`{code, message, details, trace_id, retryable}`。错误详情不得泄漏无权项目的存在与数据。

写入使用 CSRF 防护、请求 Schema 和服务端授权。批准/导入发布使用 `Idempotency-Key`；编辑统一用 expected_revision，首版不同时引入另一套 If-Match 版本语义。创建异步工作返回 202 和资源 ID，不能在未完成时回 200 并提示成功。

| 接口 | 作用 | 主要校验/结果 |
|---|---|---|
| POST /registrations | M1 本地注册 | 账号唯一、密码哈希、限流；只创建隔离演示项目，201；公司成员邀请另行设计 |
| POST /sessions；DELETE /sessions/current | 登录/退出 | 服务端会话、CSRF 与限流；具体契约在 M1 实施前同步 |
| GET /me；GET /projects | 当前用户与许可项目 | 不信任前端传 role |
| POST /projects/{id}/imports | 上传并建立预检任务 | 文件限制、权限、重复哈希；202 import_id |
| GET /imports/{id}；POST /imports/{id}/publish | 查看报告/发布快照 | 阻断错误不可发布；current 指针版本比较 |
| GET /projects/{id}/inventory；GET /projects/{id}/findings | 查事实/异常 | 指定 snapshot；返回 as_of、分页与单位 |
| POST /projects/{id}/runs | 创建 analyze/follow_up/draft_action | mode、question、context_refs；服务器决定可见范围 |
| GET /runs/{id}；GET /runs/{id}/events?after={cursor} | 状态/增量事件 | 每次读取鉴权；游标严格递增 |
| POST /runs/{id}/answers | 回答澄清 | interruption_id、expected_revision；服务器映射图恢复操作 |
| POST /runs/{id}/cancel | 请求取消 | 已提交任务不因取消 run 而删除 |
| GET /analyses/{id}；GET /evidence/{id} | 结果与来源 | 项目、来源版本、历史权限检查 |
| GET /drafts/{id}；PATCH /drafts/{id} | 查看/修改草稿 | expected_revision；新 revision 和 hash |
| POST /drafts/{id}/approvals | 批准/拒绝 | 审批能力、exact revision、Idempotency-Key；批准 202，已记录拒绝 200 |
| GET /approvals/{id} | 查询提交结果 | pending/committed/conflicted/rejected；committed 才有 task_id |
| GET /projects/{id}/tasks；PATCH /tasks/{id} | 查询/更新内部任务 | 当前用户、状态转移、revision；完成必须有结果 |
| POST /projects/{id}/documents；POST /document-versions/{id}/publish | 上传/发布知识 | 解析、权限、生效冲突、索引完成 |
| POST /document-versions/{id}/retire | 停用版本 | 发布权限、原因，影响未提交草稿 |
| POST /feedback | 分析/建议反馈 | 绑定 target_revision，保存原文和分类 |

聊天 session_id 只做上下文分组，与 /sessions 管理的登录会话不同；每次分析有独立 run_id。API 不接受用户构造的 LangGraph Command 或 thread_id 作为授权操作。

## 5. 批准与写入的精确语义

用户提交 draft_id、revision、负责人和截止时间的最后修改必须已保存；批准接口只接受已保存 revision，不边批准边替换正文。服务端读取该 revision，计算关联证据哈希，不接受模型/浏览器提供的 approval_token 当事实。

审批事务写 approvals(pending)+resume_job+audit，响应 202“已收到批准，正在建立待办”。worker 取得任务后重查权限、证据、草稿版本和取消状态，应用服务在事务中将 approval 置 committed、draft 置 approved、建立唯一 task、写 task_event 和 run_event。

若冲突则 approval=conflicted，草稿 expired/superseded，UI 显示重审入口；没有 task。批准按钮网络超时，通过 approval 查询和原 key 重试，不重新生成 key。

唯一约束至少覆盖 `(org_id, approval_id)` 的任务创建和 `(actor_id, route, idempotency_key)` 的请求记录；同 key 不同请求体返回 409。不同 key 对同 draft_revision 的重复批准也只能产生一个有效提交。

## 6. 数据集迁移映射

现有 hospitals → projects；inventory_snapshots/batches → 一次 synthetic snapshot_set；consumption_daily → 日记录；purchase_orders → 订单/行；knowledge_manifest → synthetic document_versions；gold_cases → 规则和 AI 评测输入。

现有 `frontend/public/demo-data.json` 是为显示裁剪的数据投影，不是后端规范；本地 localStorage 任务不迁入正式试点。新后端模型实施时建立显式 adapter 和字段校验，不能让前端写死的案例文字成为业务真相。
