## 优先修正与优化

### P1：当前体验和可信度

1. **首页重点关注没有纳入效期异常。** 异常中心把“检验质控材料已过期批次”列为优先核实，但首页只合并数据质量与低覆盖，再取前 4 项。首页因此遗漏这一高关注项，且列表按数据顺序而非统一业务优先级排序。应复用确定性风险报告，纳入效期、稳定排序并说明未展示条数。证据：截图 01/06；`WorkbenchApp.tsx` 的 low/attention 与 attention-list。
2. **Agent 运行成功不代表语义正确。** 本轮回看历史运行 `4c30beca-cd86-4762-ab47-310ce172c4c7`，仍将 3 项无法估算全部归为数据质量问题，实际当前规则区分为数据质量 2 项、零消耗 1 项；回答还出现 MAT-P004 拼写和内部字段名。当前代码已补原因分类和提示词，但没有新的真实模型回归证明问题已修复。应建立固定业务问题集，分别评测数值、类别、物资名称、引用支持度、未知项及草稿可执行性。
3. **控制全项目分析上下文。** 数据库只读复核上述历史运行累计 `total_tokens=87217`，是一次 run 内多次模型请求的合计，不是单条响应，也不是费用。cost 为 null。当前批次/逐日消耗可一次返回整个范围并不断带入对话，应先提供确定性摘要和异常对象，按需取明细，保留完整扫描计数及引用；增加输入 token/工具返回体预算。只限制 8 次工具与输出 token 不足以控制输入累积。
4. **快照一致性需在数据发布前补回归。** RiskPanel 请求当前 `/risks`，其“重新扫描”只刷新局部资源；页头、后续核查和明细仍从外层 dashboard 取得 snapshot_id。若另一路发布新快照，可能产生新异常列表配旧页头/操作上下文。此项是源码确认的条件性风险，本轮未修改快照复现。应将风险报告快照绑定到明细/分析，并统一刷新；保留旧分析。
5. **增加业务反馈入口。** 当前只有查看与继续分析，没有“引用不支持/数据不对/建议不适用”的持久反馈处理流程。错误历史应保留，另记录复核结论和修正版，不能直接改写原答案伪装成功。

### P2：工程维护与规模

- 路由和重组件按需加载；优先实测首屏与慢网后再调包。`WorkbenchApp.tsx` 1296 行、`M2Panels.tsx` 820 行，建议按会话、运行、草稿、任务拆分，同时保留共享表格，避免重复维护。
- 运行历史 API 上限 200，页面已诚实标注“最近 200 条”，但没有访问更早记录的游标；库存、资料、任务多为全量取回再前端分页。持续使用前需要服务器分页、过滤与明确总数。
- 词法检索每次加载有效片段并评分；库存/消耗工具多次扫描内存列表。现有小样本通过不代表蓝图中 500 种物资/10,000 片段容量通过，需按目标量级压测后优化索引和缓存。
- `/health` 只查数据库与 provider 配置，未验证 worker 心跳、排队时长或供应商可用性。补运行状态与失败聚合，不能用“AI 已配置”代替“服务健康”。
- 补可重复的浏览器关键路径回归：登录、异常→分析、引用、追问、草稿编辑确认、并发/过期冲突、任务完成与重开、断线重连。现有 9 项前端测试没有覆盖这些路径。

## 菜单如何补齐

以下是基于仓库产品蓝图与当前实现的建议，不是新增开发授权或声称行业法定必备。

| 建议一级菜单 | 现状 | 需增加的页面/子页 | 优先级 |
|---|---|---|---|
| 工作台 | 已有核查入口和运行历史 | 统一异常优先级、本人待办/超期摘要、数据新鲜度；保留 Agent 主入口 | 近期 |
| 异常中心 | 只读确定性发现清单 | 异常详情、关联任务、复核记录；无需处理原因、解决证据、跨快照复现/解除对比 | 近期迭代；不自动清除快照异常 |
| 任务中心 | 仅本人任务 | 先补待确认草稿入口、搜索、超期筛选；多人阶段再做项目任务、分派、审阅、复核 | 本人增强近期；团队依赖成员权限 |
| 数据中心 | 当前仅库存查询与批次/消耗抽屉 | 导入批次、字段映射、预检错误、质量报告、快照版本与发布；库存/批次/消耗为子页 | 下一业务里程碑优先 |
| 知识中心 | 只读目录、检索和版本阅读 | 上传/解析预览、适用范围、生效时间、版本冲突、发布/停用、索引状态 | 下一业务里程碑优先 |
| 运行与反馈 | 运行历史在工作台 | 全历史分页、失败原因、耗时/token、工具覆盖、版本、人工反馈与评测结果；运维项按权限展示 | 近期 |
| 项目与成员 | 仅首个项目；没有管理菜单 | 项目切换、成员邀请/停用、角色与能力、科室范围、本人资料与账号维护 | 团队试点前 |
| 系统设置与审计 | 主要为后端配置；局部留痕 | AI 开关、规则版本/阈值管理、配置状态、操作审计、服务与备份状态；不得在前端暴露 key | 试点前 |

这些不必拆成几十个一级入口：用 7–8 个一级菜单和必要子页即可。先补流程和 API，再增加可操作页面，避免只有菜单没有业务。

若目标扩大为完整 SPD 供应链运营系统，还需另行定义：物资/科室/库位及单位主数据、供应商与资质、订单/在途/交期、验收与入库、领用/出库/配送、退库/调拨/盘点、批次追溯/召回、对账结算、运营报表和系统集成。它们需要业务访谈、数据和权限设计，不属于 M1/M2 欠交付。当前尤其缺在途和交期查询工具，因此覆盖天数只能是库存基线。

## 推荐推进顺序与验收出口

1. **M2.1 质量与性能收口**：修首页优先级及快照一致性；Agent 语义基准、上下文预算、业务用语；首屏分包；关键 E2E。出口：固定案例逐项有依据、错误分类不混淆、历史不被覆盖、记录真实用量/耗时。
2. **M3 持续运营基础**：先做数据导入/质量/快照发布、知识版本发布和反馈观测。出口：业务维护人能发布新数据，新分析读取新版，旧引用可回看，旧草稿受阻；修正数据有审计轨迹。
3. **M4 团队试点**：成员与角色、任务分派/复核、异常生命周期、站内提醒；PostgreSQL 实际迁移/连接、备份恢复、部署监控、脱敏数据及业务人员验收。多人业务完成前，不把本人任务标为协同平台。
